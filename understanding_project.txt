1. Executive Summary
--------------------

ReleasePilotLite is a full-stack deployment tracking application built as a
backend-development learning project.

It is no longer a plain Java console project. Its current form is:

- Spring Boot REST API backend
- PostgreSQL database
- Flyway-managed database schema
- Next.js dashboard frontend
- Docker Compose local full-stack runtime
- Swagger/OpenAPI documentation
- Spring Boot Actuator health checks
- JUnit and Mockito backend tests

The application lets a user:

- create a deployment
- assign DEV, STAGING, or PRODUCTION environment
- list, filter, and paginate deployments
- view deployment details
- move a deployment through a controlled lifecycle
- record timeline events
- ingest external CI/CD events
- avoid duplicate external events through idempotency
- view summary counts on a dashboard

The current project is a functional local MVP and a strong portfolio/learning
project. It is prepared for deployment work, but it is not yet deployed to a
cloud environment and is not yet a production multi-user system.


2. Problem the Project Solves
-----------------------------

Deployment information is often spread across terminal output, CI/CD tools,
GitHub Actions pages, and team messages.

ReleasePilotLite provides one place to answer:

- Which service was deployed?
- Which version was deployed?
- Which environment received it?
- What is its current status?
- When was it created, started, and completed?
- What events happened during the deployment?
- Which CI/CD provider, branch, commit, or user triggered an event?

8. Deployment Domain Model
--------------------------

Entity:

src/main/java/com/dawood/releasepilot/deployment/Deployment.java

Database table:

deployments

Fields:

- id: generated Long primary key
- serviceName: required service identifier
- version: required deployment version
- environment: DEV, STAGING, or PRODUCTION
- status: PENDING, RUNNING, SUCCESS, or FAILED
- createdAt: creation timestamp
- startedAt: timestamp set when deployment starts
- completedAt: timestamp set on success or failure

The entity contains the lifecycle business methods:

- start()
- markSuccessful()
- markFailed()

These rules are enforced inside the domain entity:

- only PENDING can become RUNNING
- only RUNNING can become SUCCESS
- only RUNNING can become FAILED
- SUCCESS is final
- FAILED is final

This is important because lifecycle logic is kept near the state it protects,
instead of being duplicated in controllers.

10. Deployment Uniqueness
-------------------------

A deployment is unique by:

service_name + version + environment

Examples:

- payment-service + v1.0.0 + DEV: allowed once
- payment-service + v1.0.0 + STAGING: allowed separately
- payment-service + v1.0.0 + DEV again: rejected

Protection exists at two levels:

1. DeploymentService checks before saving.
2. PostgreSQL has a unique constraint.

The service throws DuplicateDeploymentException, which becomes HTTP 409
Conflict.

12. Deployment Service
----------------------

File:

src/main/java/com/dawood/releasepilot/deployment/DeploymentService.java

Responsibilities:

- validate service inputs
- prevent duplicate deployments
- create deployments
- load deployments or throw not-found errors
- list all deployments
- filter and paginate deployments
- perform lifecycle transitions
- save timeline events
- map entities to API response records

Transaction behavior:

- create/start/success/fail methods use @Transactional
- read methods use @Transactional(readOnly = true)

Every core deployment state change writes a timeline event in the same
transaction:

- creation writes PENDING / "Deployment created"
- start writes RUNNING / "Deployment started"
- success writes SUCCESS / "Deployment marked successful"
- failure writes FAILED / "Deployment marked failed"

If a transaction fails, deployment state and its event are rolled back
together.

16. CI/CD Ingestion API
-----------------------

Endpoint:

POST /api/integrations/deployment-events

Required header:

X-ReleasePilot-Token: local-dev-token

The local token is only the development default. Production reads the token
from RELEASEPILOT_INGESTION_TOKEN.

Required request fields according to backend validation:

- deploymentId
- status
- message
- provider
- externalDeploymentId

Optional metadata:

- commitSha
- branchName
- triggeredBy
- deploymentUrl

The endpoint:

1. verifies the token before the controller executes
2. validates the request
3. confirms the referenced deployment exists
4. checks whether the external event already exists
5. returns the existing event when it is a retry
6. otherwise creates a new timeline event

It returns 202 Accepted.

Important current behavior:

- ingestion attaches an event to an existing deployment
- ingestion does not create the deployment
- ingestion does not change the Deployment entity's current status
- an external timeline status can therefore differ from current deployment
  status unless the lifecycle API is also called


17. CI/CD Idempotency
---------------------

Idempotency key:

provider + externalDeploymentId + status

Why it exists:

CI/CD tools retry HTTP requests. Without idempotency, the same event could be
stored multiple times.

Implementation:

- repository lookup before save
- database unique constraint as final protection

The API returns the existing event when the same key is received again.

40. Mental Model for Learning
-----------------------------

When a user creates a deployment:

Frontend form
  -> POST /api/deployments
  -> DeploymentController
  -> request validation
  -> DeploymentService
  -> duplicate check
  -> Deployment constructor creates PENDING state
  -> DeploymentRepository.save
  -> DeploymentEvent PENDING record
  -> PostgreSQL transaction commits
  -> DeploymentResponse JSON
  -> frontend redirects to detail page

When a user starts a deployment:

Detail page button
  -> PATCH /api/deployments/{id}/start
  -> DeploymentController
  -> DeploymentService
  -> load deployment
  -> Deployment.start()
  -> state becomes RUNNING
  -> startedAt is set
  -> RUNNING timeline event saved
  -> frontend invalidates cached detail/list/dashboard data

When CI/CD sends an event:

CI/CD HTTP request
  -> token interceptor
  -> request validation
  -> ingestion service finds deployment
  -> idempotency lookup
  -> existing event returned OR new event saved
  -> 202 response
  -> event appears in deployment timeline
